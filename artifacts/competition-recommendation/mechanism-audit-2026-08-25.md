# 竞赛追问、评分与推荐机制审计报告（2026-08-25）

## 0. 审计结论与当前状态

本次修改已经形成可运行的候选实现，三类偏好追问、资格快照隔离、七维基础分修复、可信匹配校准、确定性 Top 10、DeepSeek 受限重排、四层 Top 3 和收藏 V2 均已实现。常规自动化、端到端浏览器测试和真实 DeepSeek 多轮回归通过。

但是，这一候选实现**尚不能按需求宣告“严格审核通过并正式落地”**。唯一剩余硬阻塞是：仓库不存在实施开始前、带不可变 Git 来源和逐画像结果的 `deterministic-2026-08.v11` 基线文件 `tests/fixtures/competition-score-baseline-v11.json`。因此无法可信计算 Anchor 与留出集相对旧版的平均提升是否都在 12–15 分。事后重算或伪造时间戳都不符合审计要求，故严格门禁保留失败；当前工作区未提交、未部署、未标记为验收通过。

换言之：功能与现行质量门禁已通过，真实模型也通过；“相对旧版提升 12–15 分”这一历史对照门禁因缺少真实旧基线而不可验证，所以整体结论是**候选实现完成，最终落地被严格基线门禁阻止**。

## 2. 从 14 个固定问题到签名档案

### 2.1 可见的 14 轮

前端按以下顺序显示 14 轮；一轮可包含多个相关字段。正常签名档案展开为 19 个必需字段（16 个评分字段，加 `enrollmentStatus`、`teamUnit`、`teamSize` 三个固定资格事实）；若用户在固定阶段答案中提供并确认首次高等教育年份，则为 20 个字段：

1. 学习阶段，并在同一轮确认全日制／毕业状态；
2. 主专业方向与更细的学科／技术方向；
3. 已具备技能；
4. 兴趣方向；
5. 愿意完成的核心任务形式；
6. 参赛目标，最多两项；
7. 期望成果，最多两项；
8. 项目起点；
9. 竞赛经历与现有证据；
10. 每周投入；
11. 参赛时间偏好；
12. 当前组队状态、已知队伍人数、是否同一参赛单位；
13. 可用资源与报名支持；
14. 可行参赛方式。

固定问卷仍可收集资格事实，因为这些事实发生在用户明确确认的 14 题阶段；本次禁止的是 14 题之后的动态资格追问。

### 2.2 白名单、自由文本与确认

- 每个字段都有服务端维护的枚举、最少／最多选择数和互斥规则；例如目标最多两项，`none` 不能与真实资源或证据并选。
- 前端把一轮中的结构化选择编码为 `fieldId:value`，自由文本保留原文上下文，但不会直接进入 Profile V5。
- 服务端先做 Unicode NFKC、别名和分隔符归一化；能唯一映射的答案由确定性规则处理。
- 只有无法唯一映射的自由文本才可交给低温模型；模型只能从该字段白名单返回候选值，并必须给出原文中真实存在的 evidence span。服务器决定置信度，不采信模型自报置信度。
- 冲突、歧义或未映射结果必须由用户确认；未确认解释不能升级为档案事实。
- 自由文本与动态备注上限为 120 字，并在前后端阻止姓名、电话、邮箱、学号、具体学校等个人信息。

### 2.3 签名、有效期与重建

- 归一化结果、原始回答上下文、解释结果、确认状态和最终 Profile V5 进入 HMAC-SHA256 签名令牌。
- 问卷令牌与 V5 会话令牌有效期均为 30 分钟，最大 48 KiB；签名比较使用恒定时间比较。
- 生产环境必须配置不少于 32 字符的签名密钥；开发环境的默认密钥明确不可部署。
- 令牌过期返回 `CONVERSATION_EXPIRED`，前端重新走归一化；V4 返回 `CONVERSATION_POLICY_CHANGED`，前端保留已确认的 14 题问卷令牌，只丢弃旧 transcript 与 pending question，直接重建 V5，避免重复归一化。`QUALIFICATION_SNAPSHOT_CHANGED`、`INVALID_DYNAMIC_QUESTION`和 `CONVERSATION_NOT_COMPLETED` 也采用这一已确认问卷重建路径；只有真实过期才重新发送固定问卷做归一化。
- 问答默认不写浏览器存储；只有用户主动收藏推荐后，推荐快照才写入 `localStorage`。

## 3. 资格快照与动态追问的架构隔离

### 3.1 快照如何生成

固定问卷确认后，服务器以 Profile V5、当前官方目录和评分器版本遍历每项竞赛及其真实赛道，生成 `competition-qualification-snapshot.v1`。每个条目包含：

- `eligible`、`needs_clarification` 或 `ineligible`；
- 硬过滤原因；
- 待核验原因；
- 事实级官方 `sourceRefs`；
- 每个赛道相同结构的资格结果。

只有带 HTTPS 官方来源、evidenceRef 和相应 fact 标记的目录事实才能执行硬过滤。硬过滤覆盖：当届取消、官方学段不符、全日制／在籍事实不符、官方必需资源缺失、无替代条款的首次高教年份门槛、同一参赛单位冲突和已确认队伍人数冲突。证据不完整时保守进入 `needs_clarification`，不会猜成合格或不合格。

若竞赛含赛道：任一赛道 `eligible` 则母项可为 `eligible`；否则任一赛道待核验则母项待核验；全部赛道硬性不合格才将母项判为 `ineligible`。

### 3.2 快照如何冻结与校验

- V5 会话令牌不塞入整份快照，而保存快照条目数、评估时间和规范 JSON 的 SHA-256 摘要，同时锁定目录与评分器版本。
- 每一轮 clarify 和最终 recommend 都用签名 Profile、同一评估时间、当前目录和评分器重新生成快照，再比对摘要与条目数。
- 快照构造函数没有 transcript 参数；硬过滤函数也不接受动态 transcript。这是类型和函数签名层面的隔离。
- `competition-fit` 与 `candidate-goal-tradeoff` 只能改变偏好分与排序，资格状态、原因、硬过滤结果和来源完全不变。
- `track:<competitionId>` 只能展示快照中非 `ineligible` 且目录允许偏好选择的赛道。提交后服务器再次验证问题选项和答案都属于该集合；未知或硬性不合格赛道会被拒绝。
- 赛道选择只采用预计算赛道状态；`needs_clarification` 不会因用户选择升级，动态回答也不会成为官方资格证据。

这使截图中“已核对且符合”“仍需核对”“已确认不符合”等资格问答无法由新版 schema、令牌或路由表达。

## 4. 三类动态追问

### 4.1 唯一合法信号

V3 schema 只接受：

- `competition-fit`：能力与任务偏好，多选，最多两项；
- `candidate-goal-tradeoff`：候选目标取舍，单选，2–4 个目标；
- `track:<competitionId>`：具体竞赛赛道偏好，单选。

schema 同时拒绝资格、官方条件、全日制、学籍、学历、出生／入学、学校、地区、人数、参赛单位、申诉、身份赛道等文案，也拒绝 URL、Markdown、个人信息索取、重复选项、非白名单值和不安全问题 ID。

问题文案与选项均由服务器模板和目录生成，DeepSeek 不参与选题或题目写作。自由文本归一化可使用 DeepSeek，但仍只能映射回签名问题的白名单值，并须再次让用户确认。

### 4.2 反事实信息增益

每轮对问题的所有合法单选答案，以及能力题允许的两两组合，重新运行生产评分与最终可见 Top 3 选择。反事实签名只包含：

- Top 3 成员；
- Top 3 相对顺序；
- 被比较竞赛在可见 Top 3 中的推荐赛道。

资格状态不在反事实签名中；仅分数小幅变化但最终成员、顺序和赛道不变，也不会产生“material”问题。至少出现两种不同可见结果才有自动追问价值。

能力题会先评估服务器全部候选能力标签，再选择在 UI 上产生最多不同结果的至多 8 个选项。目标题优先采用固定问卷已选目标；不足两项时按当前候选间的目录匹配离散度补一个白名单目标。赛道题只比较冻结快照允许的赛道。

### 4.3 顺序、次数和停止

- 总数最多 3；fit、goal、track 三个问题族各最多出现一次，所有 `track:*` 共用一个族。
- 按不同反事实结果数从高到低选题；相同则按能力偏好、目标取舍、赛道偏好排序，再以 signalKey 稳定排序。
- 每次回答后从新候选与已有 transcript 重新计算；没有剩余 material 问题或达到 3 题即结束。
- 候选少于 3 个时不提问、不制造候选，最终 API 返回 `COMPETITION_CATALOG_COVERAGE_INSUFFICIENT`。

### 4.4 无高价值问题

如果固定 14 题后没有 material 问题，响应为 `optional_question`，只提供一个目标取舍题，同时页面说明当前信息已足够、顺序可能不变。用户可以：

- `skip_optional`：不提交虚假答案，直接签发 completed 令牌；
- 主动回答一次：该题标为 `optional`，回答后立即结束，不再出现后续问题。

一旦已经回答 material 问题，后续没有信息增益就直接完成，不再额外塞低价值问题。

## 5. 七维结构化基础分

基础分是七个独立舍入到 0.1 分的维度之和；未知维度按 0 计，不重新放大其他维度。上限固定为 100：

| 维度 | 上限 | 当前计算 |
| --- | ---: | --- |
| `subjectTask` | 25 | 细学科／主专业、固定任务形式、兴趣、语义任务原型和学段特异性；当前档案语义原型权重 0.43 |
| `skillsEvidence` | 20 | 0.75 × 直接技能覆盖 + 0.25 × 可展示证据覆盖 |
| `goalsOutputs` | 15 | 固定目标加权匹配与期望成果匹配；可由目标取舍做 75/25 细化 |
| `maturity` | 10 | 只平均实际存在的经验—难度匹配与起点匹配；都不存在才为 0 |
| `teamResources` | 15 | 当前档案只平均每周投入、团队状态、可用资源三个适用字段 |
| `availabilityTiming` | 10 | 参赛方式与参赛时间／目录开放状态；未知不被乐观放大 |
| `dataConfidence` | 5 | 0.5 × 目录可信度 + 0.3 × 数据完整度 + 0.2 × 官方事实证据覆盖 |

### 5.1 专业与任务细节

1. 学科背景：有细学科时为 0.7 × 细学科匹配 + 0.3 × 主专业匹配；否则使用主专业匹配。
2. 任务意图：固定任务形式为主；如果回答能力偏好，则以 0.65 × 固定任务 + 0.35 × 能力偏好细化；再与兴趣按 0.85/0.15 合成。
3. 背景与任务按 0.5/0.5 合成，再以当前 Profile V5 的 0.43 语义任务原型权重细化；旧版适配器仍保留旧权重 0.55。
4. 若目录存在学段特异性，以上结果占 0.85、学段特异性占 0.15。
5. 已确认主学科与任务原型都不命中时，`subjectTask` 最多 7.4；可迁移技能、目标、团队资源分别乘 0.60、0.60、0.75，避免跨领域候选伪装成强匹配。

### 5.2 目标与成果

固定问卷目标使用以下权重：项目 1.00、奖项 1.15、科研升学 1.10、就业 1.00、作品集 1.00、创业 1.00、人脉 0.85。固定目标匹配与成果类型在两者都存在时按 0.70/0.30 合成。

若用户回答目标取舍：

```text
originalGoalOutputRatio = 固定目标与期望成果得到的比例
priorityRatio = 当前竞赛在追问所选目标上的目录匹配值
refinedGoalOutputRatio = 0.75 × originalGoalOutputRatio + 0.25 × priorityRatio
```

它只改 `goalsOutputs`，不会产生额外 bonus，也不改资格、可信度、官方事实或获奖概率。

### 5.3 结构性低估修复

- `maturity` 不再因为经验难度或起点其中一项缺失就把缺失项当 0 拉低平均值；只对存在项平均。
- Profile V5 的 `teamResources` 不再混入旧版 constraint 字段，只平均每周投入、组队状态和可用资源中可计算的项。
- 动态团队资格回答已经从 V3 类型中消失，不能提高资源分。
- 官方资格、赛期、参赛方式的未知值仍保守处理，没有为了提分而改成“已满足”。

## 6. 综合匹配分校准

`baseMatchScore` 继续用于结构化召回、质量门槛和提供给 DeepSeek 的只读上下文；页面展示 `matchScore`。校准不直接改推荐排序。

```text
alignment =
  0.50 × subjectTask / 25 +
  0.30 × skillsEvidence / 20 +
  0.20 × goalsOutputs / 15

evidenceConfidence = dataConfidence / 5

qualified =
  profileActionability >= 0.35 &&
  baseMatchScore >= 55 &&
  subjectTask >= 7.5 &&
  teamResources >= 3

adjustment = qualified
  ? round1(min(
      8,
      (100 - baseMatchScore) × 0.60 × alignment × evidenceConfidence
    ))
  : 0

matchScore = round1(min(95, baseMatchScore + adjustment))
```

`profileActionability` 只由可执行档案信号组成：非 other 专业 0.20，现有证据 0.20，非纯想法起点 0.15，有参赛经历 0.15，每周不低于 5 小时 0.10，有资源 0.10，有技能 0.05，非坚持单人 0.05，固定资格事实已确认 0.05。

弱匹配、无匹配、低可执行性以及 `reference` 的 adjustment 均为 0；上限 8，综合分上限 95，不存在 100。页面明确展示“结构化基础分 X + 可信匹配校准 Y = 综合匹配分 Z”，并声明它不是获奖概率。

## 7. 从全目录到确定性 Top 10

1. 对母项及每个真实赛道分别评分；赛道沿用官方证据边界。
2. 硬性不合格评分单元被删除；同一竞赛只保留最高分赛道，竞赛去重。
3. 默认按基础分降序、同分时按开放状态和稳定 ID 排序。
4. 根据用户时间偏好，把当前／即将开放、时间待核验、下届备赛做确定性分组，但匹配优先；召回上限为 10。可用候选至少 10 项时恰好返回 10 项；只有 3–9 项时完整返回现有项，不为凑 10 伪造候选。
5. 为防止通用高分淹没明确细学科，最多保护 4 个有已确认细学科命中的候选。
6. 回答 `competition-fit` 后，可从全目录补回最多 3 个完整覆盖该偏好的强候选，并保持 Top 10 总数不变；这只影响召回可见性，不改分和资格。

质量候选池是以下并集：已确认主学科命中，或已确认任务形式存在语义任务原型命中。固定题路径的质量排序使用：

```text
baseMatchScore + subjectTask + 4 × semanticArchetypeFit
```

有偏好 transcript 后，不重复加固定语义项；能力偏好以有界比较器权重处理，单项最多 24，双项覆盖最多 18，从 Top 10 外按偏好补回的候选另有最多 8 点可见性权重。以上都不是分数，只用于已通过资格和质量边界的顺序比较。赛道选择若自然排在前三之外，只保留在第三槽，防止用户刚选择的赛道完全不可见，同时不强行升为第一。

## 8. DeepSeek 的权限边界

DeepSeek 收到：

- 去除原始问卷文本后的 Profile V5 白名单档案；
- 仅三类 V3 偏好 transcript；
- 服务端生成的最多 10 个候选、基础分、分项、预计算资格、推荐赛道和类型化证据目录。

模型必须返回所有候选 ID 的完整、无重复排列：通常是 Top 10；目录经过硬过滤只剩 3–9 项时则是该完整集合。每个匹配理由、差距和建议只能引用该候选对应类型的 evidence ref。Zod 校验器拒绝少项、重复、新增竞赛、跨候选引用、错类型引用或非法事实。证据校验使用与提示词完全相同的压缩 evidence catalog；即使模型猜中服务器内部存在但未暴露的 ref，也必须整体回退。

服务器始终保留权威字段：分数、校准、资格、官方来源、赛道和候选集合都不从模型输出读取。模型只决定排列及从已有证据目录选择引用；服务器再展开证据文字。

模型采用温度 0、最多两次协议尝试。非法输出、无效 JSON、超时或不可用时，对完整确定性候选使用 `rule-fallback`，不会丢候选、恢复明确不合格项或编造事实。

竞赛页的同意文案明确将第三方接收方限定为 DeepSeek。因此，虽然全站通用 AI 客户端仍支持 `openai-compatible` 供其他功能使用，竞赛的固定问卷归一化、动态文本归一化、排序和解释路径均单独做提供方失败关闭：生产只允许 `AI_PROVIDER=deepseek`，其他值在网络请求前返回 `provider_not_allowed` 并使用本地确定性结果。`mock` 只有在 `ALLOW_AI_MOCK=1` 和 `AI_TEST_MODE=1` 同时存在时才可进入测试降级路径，且不发起上游请求。部署脚本与生产预检同时强制 DeepSeek，作为第二道边界。

需要区分“协议合法”和“语义质量”：单次返回的学科优先、时效优先和偏好顺序主要受提示词约束，不是可由 schema 独立证明的逻辑定理。服务器会在模型后继续应用质量候选池、四层 Top 3、资格不可变和证据绑定；离线金标与真实 DeepSeek 回归则作为语义质量门禁。因此，一个结构完整但语义排序较差的输出不会仅因“主观排序不佳”触发协议 fallback；它会被后处理边界限制，并必须在金标／真实模型门禁中维持达标。

## 9. 最终三项与标签

若至少有 3 个未被硬排除的候选，服务器按进入顺序从以下四层填满 3 个不同竞赛：

1. 评分校准条件通过且资格 `eligible`；
2. 评分校准条件通过且资格 `needs_clarification`；
3. 评分校准条件未通过且资格 `eligible`；
4. 评分校准条件未通过且资格 `needs_clarification`。

第 3、4 层强制 `recommendationRole=reference` 且 adjustment=0。第 1 名只有通过校准门槛才是 `best`／“最匹配”；否则也是“参考匹配”。其余通过门槛项是 `steady`／“稳妥选择”。资格待核验项显示原因；明确 `ineligible` 从评分阶段已消失，永不补位。

若未被硬排除的不同竞赛少于 3 个，API 返回目录覆盖不足错误，不伪造第三项。推荐顺序使用基础分、固定档案、偏好和证据；展示校准增量不参与排序。

## 10. 收藏、隐私、版本与异常

- 存储 key 保持 `saitu.savedCompetitions.v1`，保证旧数据仍可发现；内部 schema 升为 `saitu.savedCompetitions.v2`。
- V2 保存响应版本、目录／评分器／提示词版本、基础分、综合分、校准、七维明细、排名来源、回退信息和解释。
- 旧 V1 仅接受严格旧六维结构并在读取时内存迁移为 `legacyScore:true`；界面只显示“历史基础分”，不会反推当前综合分。迁移不会为了改版本而单独写盘；用户随后保存或删除收藏时才持久化为 V2。
- 已退役 ID 只有在仍是同一竞赛稳定身份时才允许展示当前目录详情；当前两个“替代服务”映射并非同一赛事，收藏页因此明确进入“该竞赛已不在当前目录中”分支，不会把另一赛事的名称／封面与旧分数、旧理由混合展示。
- V2 校验七维上限、七维和等于基础分、校准公式、综合分上限和角色枚举；损坏、配额、不可用分别返回可诊断错误。
- AI 请求需要显式同意，有请求体大小、分钟与每日限流、`no-store` 响应和结构化错误码；竞赛模型路径在上游请求前还会验证“实际提供方 = 同意文案披露的 DeepSeek”。
- 旧令牌、过期、资格快照变化、非法问题、会话未完成、目录覆盖不足和模型失败都有独立错误路径；策略变化、快照变化、非法问题和会话状态冲突复用已确认问卷重建 V5，真实过期才重新归一化。重试保持幂等语义，不用伪答案推进会话。

## 12. 失败迭代与修正记录

严格审核期间发现并修正了以下问题，每次修正后重跑相关门禁：

1. V4 策略变更恢复路径曾重复调用固定问卷归一化；改为复用已确认问卷令牌，仅真实过期才重新归一化。
2. 前端最初把策略变更与真实过期合并处理；按服务端错误码拆分，避免错误恢复。
3. 连续两轮 E2E 的测试助手把能力多选当成单选；改为按真实问题 selection 使用 checkbox。
4. 服务外包偏好画像中，一个完整支持用户能力选择的候选位于固定 Top 10 外；增加有界的偏好二次召回，仍保持完整 Top 10、最多补回 3 项且不改分／资格。
5. AI research 画像被宽泛软件标签挤压；把“目录展示技能”与“可计分技能证据”分离，并补足 AI research 语义原型特异性，恢复准确 Top 3，同时维持 25 个留出画像指标。
6. 浏览器恢复测试暴露 `CONVERSATION_POLICY_CHANGED` 与 `CONVERSATION_EXPIRED` 语义差异；修正后全量 Playwright 转绿。
7. 严格旧版相对提升门禁发现真实历史基线缺失；没有降低门槛、改金标或事后伪造基线，而是保留为明确阻塞。
8. 最终收藏审计发现两个退役 ID 曾被解析到并非同一身份的替代赛事，造成“新赛事资料 + 旧赛事快照”的风险；收藏页改为只按稳定 canonical ID 解析，退役项走“已不在当前目录”分支，并增加身份边界回归断言。
9. 会话恢复审计发现快照变化等 409 错误会在原请求上永久重试；将 `QUALIFICATION_SNAPSHOT_CHANGED`、`INVALID_DYNAMIC_QUESTION`、`CONVERSATION_NOT_COMPLETED` 纳入会话重建矩阵，复用已确认问卷且不伪造答案。
10. 证据引用审计发现旧校验范围比模型实际看到的压缩目录更宽；改为只允许 prompt 真实暴露的 ref，并注入“可猜测但未暴露”的服务器 ref 验证必须回退。
11. 提供方审计发现通用 AI 客户端默认可走 OpenAI-compatible，与竞赛页只披露 DeepSeek 不一致；在所有竞赛模型路径增加 provider fail-closed，其他 provider 在 fetch 之前返回 `provider_not_allowed`，并增加归一化与排序的“零网络请求”回归测试。
12. 资格证据审计发现“当届取消”需要与其他目录证据严格区分；取消硬过滤改为必须存在事实范围为 `schedule` 的官方证据，只有未验证的取消描述时降为 `needs_clarification`，不得直接排除。
13. 评分适用字段审计发现 Profile V5 的 `teamResources` 仍可能隐式读取固定资格字段 `teamSize`；彻底移除该输入，只保留每周投入、团队状态和可用资源。旧 Profile 的约束字段继续仅由隔离适配器处理，旧版语义原型权重固定为 0.55。
14. 动态自由文本确认曾可能在“合法结构化选项 + 原始备注”之间重复要求确认；新增 `interpretationConfirmed` 的明确确认状态，同时兼容已提交合法选项的旧客户端请求，并从签名 transcript 中去掉原始备注，避免重复循环和不必要的文本留存。
15. 目标题的信息增益曾把“赛道变化但 Top 3 竞赛成员／顺序不变”误算为目标取舍的 material 结果；目标题反事实签名改为只比较有序 Top 3 竞赛 ID，赛道变化只由赛道题负责。
16. 同意审计与隐私复核发现本地确定性失败不应被记录成 DeepSeek 上游处理；审计记录改为只有实际尝试上游时才标记 DeepSeek，纯本地路径标记 server。最终排序提示词同时确认不接收 14 题原始文本，只接收已确认的白名单 Profile V5。
17. 最后几次评分、资格证据和 materiality 修复使旧的真实模型结果失效；没有沿用旧数据，而是在最终业务代码固定后完整重跑 21×3，得到新的 63/63 结果。随后未再修改评分、资格、路由或排序生产代码。
